Builds on D-201 (the bytecode), D-227 (the level `-O n`, 0 to 10, implicit 1), D-196 (an optimization starts with a measure before and after) and `design-bytecode.md` §16 (the plan of B5.3 to B5.6). This page has two parts: the levels (what each level of `-O` does to the bytecode) and the notes (every optimization found while the bridge goes away, with its level, its cost and its state). The notes only grow; a note that is done says where and how much it gave.

## 1. The rule of the levels

`spec/semantics/variables.md#optimization-level` already says it: "higher levels spend more time compiling and less time running". For the bytecode that becomes four bands, each a superset of the one below. A higher band adds **passes** (compile time and code in `evecp`) or **run-time work that pays only in long runs** (memory, warm-up).

| Band | Levels | For | Compile-time budget | What it adds |
|---|---|---|---|---|
| **Debug** | 0 | the debugger, a failing test, a teaching run | none: the emitter alone | nothing: one statement after another as written, every temporary in its own register, a safe point after every statement, no fused instruction; the listing reads like the source |
| **Quick** (the implicit level) | 1 to 2 | a script that runs once, the REPL, the tests | linear in the size of the routine, one pass | the cheap local choices of the emitter: immediates, fused compare-and-jump, typed instructions when the checker knows both types, constants as values at load, no `move` to a register that is overwritten at once |
| **Steady** | 3 to 5 | a service, a job that runs for minutes | a few passes over the code of a routine (peephole, liveness), still linear | inline caches of names and methods, quickening (a generic instruction rewrites itself into its typed form after it saw the types), superinstructions, dead stores, `safe` points only where something was allocated; level 5 also loads the meta tables in memory (D-227) |
| **Long** | 6 to 10 | a server, a large ETL project | whole-program: the routines of the project and of `lib/` together | inlining of small leaf routines, constant propagation over modules, the resolution of module members at load, bounds checks dropped where a `for` proves the index; later, not scheduled, the native code of `lib/` (AOT, D-241) |

Rules:
- **Same result at every level.** Output, errors, codes and the order of effects never depend on the level; only time and memory do. The sweep `runtest.py all --both` runs at the implicit level; `bctest.py` runs the golden listings at level 1 and each optimization adds a test that runs at 0 and at its own level with the same `/*@expect*/`.
- **The listing says the level.** `eve --disasm -O n` shows the code of that level; the golden listings of `test/bytecode/` are made at level 1.
- **The level is read once**, by the emitter at the start of a compilation (`evecm.optimization.level`); the machine reads it only for run-time features (quickening, caches).
- **An `.evb` file records the level** it was compiled with (B5.7); the machine may re-optimize a low-level file at load, never lower a high one.

## 2. Notes: optimizations found while the bridge goes away

One line each: what, band, cost (compile or code), expected gain, prerequisite, state. Measures are ReleaseSafe, `bmark.py`, median of the runs.

| Id | What | Band | Cost | Expected gain | Needs | State |
|---|---|---|---|---|---|---|
| OPT-01 | **Integer fast path inside the loop**: `add`, `sub`, `mul`, `lt`... test `.int` on both registers and compute with an overflow check in `bcvm` before calling `applyOp` | Quick | none (the machine) | 10% to 30% on `p1a`, `p1b` | none | open |
| OPT-02 | **Fused compare and jump**: `if a < b` emits `jlt a b off` (and `jle`, `jeq`, ...) instead of `lt t a b; jf t off`: one dispatch and one register write less | Quick | the emitter (a condition compiler) | 5% to 15% on loops and `if` | none | open |
| OPT-03 | **Constants as values at load**: the constant pool becomes a `[]Value` made once (strings interned once by `staticStr`), `loadk` is a copy | Quick | the loader | small per `loadk`, large for string constants in loops | none | open |
| OPT-04 | **The line only on the slow path**: `it.line = c.lines[at]` is written before most instructions; the machine can keep the pc in the frame and set the line from the line table only when a native or an error needs it | Quick | the machine, the error path | 3% to 8% on every program | errors read the line through a function | open |
| OPT-05 | **One frame record per call**: a call pushes both a bytecode `Frame` and a tree walker `frames` entry (for traces); build the trace from the bytecode frames when an error is reported | Quick | the machine, `Report` | `p1b_calls` 10% | OPT-04 | open |
| OPT-06 | **`forloop` without the rune test**: the loop counter is tested for `.sym` at every pass; the emitter knows when both bounds are integers (`forloopi`) | Quick | the emitter | 2% to 5% on counted loops | the type of the bounds from the checker | open |
| OPT-07 | **Typed arithmetic**: `addi`, `addr`, `lti` when the checker knows both operands are `Integer` or `Real` (design-bytecode.md §3.3) | Quick | the emitter reads `ty` | 20% to 40% on numeric loops | the types of expressions from the checker | open |
| OPT-08 | **Arguments in place**: a call evaluates each argument into a new temporary, then the callee's window starts there; a local that is already in the right register needs no `move` | Quick | the emitter | small | none | in part (B5.3a): the window starts at the destination when it is the last temporary, so no `move` follows a call; literal arguments of a call site have no register; a local argument is still copied into the window |
| OPT-09 | **Quickening**: a generic `add` that sees two integers rewrites itself into `addi` in a run-time copy of the code (the `.evb` stays unchanged, its hash too) and falls back to `add` when it sees something else | Steady | the machine, a writable copy of the code | 20% to 40% where the checker does not know the types | OPT-07 | open |
| OPT-10 | **Inline cache of names**: `loadg`/`storeg` by name search the scopes each time; cache the `*Var` found and the scope generation in a side table per instruction | Steady | memory per instruction | large for module state and closures (`p3c`, `p2b`) | B5.3b | open |
| OPT-11 | **Inline cache of methods**: the class of the last receiver and the routine found, per call site | Steady | memory per call site | `p3b_objects` 20% to 50% | B5.4a | open |
| OPT-12 | **Value natives (R5)**: the adapter binds arguments to hidden names for natives that read nodes; natives that take `[]Value` (the fast call of D-220 shows the shape) remove the scope | Quick | the library, routine by routine | 30% to 60% per native call | none; one module at a time, the hottest first (`round`, string methods) | open |
| OPT-13 | **Safe points only where needed**: `safe` follows every statement of `main`; the emitter knows when a statement allocated nothing | Steady | the emitter (an "allocates" flag per expression) | small; fewer heap scans | none | open |
| OPT-14 | **Clear on return**: `ret` clears every register of the frame with the counted write; the heap-less ones need no count, a frame without heap values can drop the loop | Quick | the machine | `p1b_calls` 5% | none | open |
| OPT-15 | **Compile time of the emitter**: `konst` searches the pool linearly (quadratic in the constants), `routineIndex` and `find` search lists by name, and every routine is compiled twice (a trial, then for real) | Quick | the emitter | compile time of large modules (the library) | none | open |
| OPT-16 | **Superinstructions**: the frequent pairs of the profile (`EVE_PROFILE` counts by opcode) become one instruction (`loadi`+`add` as `addk`, `index`+`move`, `move`+`ret`) | Steady | the emitter, the machine | 5% to 15% | the opcode profile | open |
| OPT-17 | **Inlining of small leaf routines**: a routine of a few instructions with no call, no error handler and no capture is copied into its caller | Long | the emitter, whole program | `p1b`, `p3a` 20% to 40% | B5.3b | open |
| OPT-18 | **Members of modules at load**: `m.f(...)` and `m.c` are resolved once when the module is loaded, not by name at each call | Long | the loader | `p3a_modules` 30% | B5.4c | open |
| OPT-19 | **Bounds checks dropped** in `for i in 1..xs.count()` over `xs[i]` when `xs` does not change size in the body | Long | the emitter (a proof per loop) | collection loops 10% | OPT-07 | open |
| OPT-20 | **The `Value` layout** (D-201: version 0.8): 24 bytes and five integer tags; 16 bytes or NaN boxing halves the memory traffic of registers | Long | every module | 10% to 30% everywhere | a decision of the author | postponed to 0.8 |
| OPT-21 | **Native `lib/` (AOT through Zig)**: the routines of the library compiled to native code at the release | Long | a compiler back end, months | 2x to 5x on library-heavy code (`design/compiler-fesability.md`) | B5.7 | later, not scheduled (D-241); no JIT |
| OPT-22 | **External routines allocate per call**: `runRoutine` of an `external` routine (a native of a module, `lib/time.eve`...) makes a name node for each parameter with the long-lived allocator at every call (never freed) and searches the loaded modules under a lock to find its module | Quick | the tree walker (both engines use it) | a leak per call and its time; large for native calls in loops | none | open |
| OPT-23 | **Members of a module per call**: `moduleMember` searches the exports of the module and makes a new `Func` at each `m.f(...)`, so the fast code of D-220 (`f.fast`) is found again at every call | Quick | a table of members per module, filled at the first use | `p3a_modules`, every `lib/` call | none | open |
| OPT-24 | **Named receivers per call**: `time.format(...)`, `money.of(...)`: the machine looks the name up through the scopes at every call (`call_named`); a module or a type never changes, so the site can keep it after the first lookup | Steady | one cached value per call site | 5% to 10% on library calls in loops | a writable side table of the chunk (OPT-09) | open |
| OPT-25 | **The loop is sensitive to its own size**: the arm of the new `call` instruction made `p1a_arith` 7% slower with the same listing, and the test of `heapless` written as the complement of the heap kinds was slower than the list of the plain kinds; keep slow paths out of `execute` (`noinline`), measure `p1a` and `p1b` for every new instruction, and look at the size of `execute` in the release build | Quick | discipline, a check in `bmark.py` | keeps the gains of the others | none | rule (B5.3a) |
| OPT-26 | **Unary minus keeps its temporary**: `-x` and `not x` take an operand register that is not given back until the end of the expression (the emitter does not restore `free`), so more registers are used and a window can not start at its destination | Quick | the emitter | small | none | open |

| OPT-28 | **A region per call**: every frame of a routine enters a heap region and leaves it at `ret` (the destructors run at the safe points of the region that made the object, D-151, as in the tree walker); `p1b_calls` pays 5% for it. | OPT-29 | **The table of compiled routines at each call**: `routineFor` takes the shared lock and searches the table at every call of a routine; the `Func` value (or the call site) can keep the entry after the first call | Quick | one field in `Func`, or a side table per call site | 3% to 8% on call-heavy code | OPT-24 for the call site | open |
| OPT-30 | **One resolution per call**: a `call` looked up its target twice (once to see whether a frame can be pushed, once for the native) and `moduleMember` searched the exports both times: `p1f_complex` lost 22% until the target was resolved once (`resolveTarget`) | Quick | done | 22% on `p1f_complex` | none | done (B5.3b) |
| OPT-31 | **Stacks of nested runs**: the first design took the registers again from the interpreter at every instruction (the stack could move under a waiting run); a stack per nested run removed that cost (`p1a_arith` +24% to 0%) | Quick | done | see the note | none | done (B5.3b) |
