# How the manual is made

The manual (`manual/`) documents the Eve implementation for its users: how to use `eve` and the other programs, which features work, how the tests stand and how fast it is. It is shipped in every distribution, so **a page of the manual names no folder of the repository** (`design/`, `backlog/`, `test/`, `script/`): it links only to its own pages, and to the specification and the tutorial by their web addresses. This page is the maintainers' side: what is written by hand, what is generated, and by what.

## Layout

```
manual/
  README.md            the front page; its blocks GEN:progress and GEN:links are written by script/relnotes.py
  usage.md             the eve command line (by hand)
  features.md          template page, blocks generated by generator/evegen.py from spec/features/*.json
  tests.md             template page, blocks generated by generator/evegen.py from test/*/<suite>.json
  performance.md       template page, blocks generated by generator/evegen.py from test/bmark/history.json
  levels/              GENERATED whole by generator/evegen.py: a page per level (features, text, an example that runs)
  reference/           GENERATED whole by generator/evegen.py from spec/lexical/*.json: keywords, operators, delimiters
  release/
    README.md          the list of releases (block GEN:releases, script/relnotes.py)
    vX.Y.Z.md          the notes of each release (generated parts + hand-written parts; policy: design/release.md)
  code/evevm/ code/evecp/ code/evecm/ drivers/duckdb/ code/evetx/ code/eveux/ code/evewp/
                       GENERATED: a copy of code/<component>/doc/ (generator/evegen.py); edit the original, never the copy
```

The templates of the generated pages are in `generator/templates/`, the one of the release notes in `design/template/release-notes.md`. A page is made from its template when it is missing; afterwards only its `GEN` blocks are written again, and the text around them is kept, so the introduction of a page is edited in the page itself.

**Links in a component doc.** The files of `code/<component>/doc/` are written for their place in the manual, `manual/<component>/`: a link to another page of the manual is `../usage.md`, `../features.md`, `../evedb/README.md`. In the source folder these links look broken (`mdlinks.py check evevm` reports them); check them in the copy: `python generator/evegen.py manual && python script/mdlinks.py check manual`.

## Commands

| Command | Does |
|---|---|
| `./run.sh build manual` | refreshes everything that is generated from the spec and the source: the tutorial keywords and test pages, `lib/doc`, the generated pages and the component copies of `manual/`, the progress of `manual/README.md` |
| `python generator/evegen.py manual [--check]` | only the generated pages and the component copies of `manual/` |
| `python generator/evegen.py check` | the rules between the spec, the tests and the manual (`generator/README.md`) |
| `python generator/evegen.py manual --out <folder>` | the same pages written into a distribution, without touching the repository (`script/dist.py` uses it) |
| `python script/relnotes.py --manual` | the blocks of `manual/README.md` between releases |
| `python script/relnotes.py --check` | the links of `manual/` and the list of releases |

## Planned: support tables against the specification

Not built yet (`backlog/tech-debt.md`, TD-43). The idea, kept from the first plan of the manual: tables that compare, item by item, what the specification defines and what an implementation supports, so that other Eve compilers can publish the same tables (D-003: many compilers, one specification).

### Feature tables

Every table in `manual/support-tables/` would be generated. The generator reads:

1. **Spec JSON** (`spec/**/*.json`): one row per item, using its `id`, `status` and `ref`.
2. **Spec grammar**: one row per rule defined in a fenced `ebnf` block.
3. **Support data** (`support/*.json`): the status of each feature in each implementation.

Rows are spec features, columns are implementations, so one table compares every compiler that has a support file. A generated file starts with a comment naming its generator and inputs. Running the generator with `--check` fails when a table is out of date, or when a support file names a feature id that the spec does not define.

#### Feature ids

A feature id is `<source>:<id>`, so ids stay unique across files:

| Source | Example | Taken from |
|---|---|---|
| `keyword` | `keyword:aspect` | `spec/lexical/keywords.json` |
| `operator` | `operator:assign` | `spec/lexical/operators.json` |
| `delimiter` | `delimiter:block-comment` | `spec/lexical/delimiters.json` |
| `rule` | `rule:statement` | `ebnf` blocks in `spec/syntax/` |
| `type` | `type:Integer` | `spec/semantics/types.json` |
| `builtin` | `builtin:print` | `spec/library/builtins.json` |

#### Support data

```json
{
  "$schema": "../schema/support.schema.json",
  "implementation": "eve",
  "version": "0.1.0",
  "specVersion": "0.1-draft",
  "features": {
    "keyword:aspect": { "status": "yes" },
    "rule:statement": { "status": "partial", "note": "no line continuation yet" }
  }
}
```

| Status | Meaning |
|---|---|
| `yes` | Implemented and covered by conformance tests |
| `partial` | Implemented with limits; `note` says which |
| `planned` | Scheduled for a named version |
| `no` | Not implemented. A feature missing from the file counts as `no` |
