# Eve plan and design

The plan of the Eve project: the order of the work, the open questions, the open steps and the designs of the parts. Eve is an open standard meant to have **many compilers**: students build their own from the specification and prove it against the conformance tests.

What is not here: the language is in `spec/` (with its features, `spec/features/`), the tests in `test/`, the manual in `manual/`. Those three never name this folder; `generator/` joins them.

## Tracking with few tokens

Do not read the logs whole.

| Command | Prints |
|---|---|
| `python script/plan.py status` | the focus, the open steps and the open questions (about 40 lines) |
| `python script/plan.py show D-087 Q-035` | a live entry in full; a settled one as its line of the index |
| `python script/plan.py list` | every id and title |
| `python script/plan.py features open 6` | one line per feature, filtered by status and level (`spec/features/`) |
| `python script/plan.py feature F-NET-02` | a feature: level, status, summary, page |
| `python script/plan.py archive [--keep K]` | moves settled entries from the live files to `decision/index.md`, keeping the last K per file (default 8) |

A step of a `phase-*.md` file is `[ ]` open, `[~]` in progress, `[x]` done (with the date and a one-line result), `[!]` blocked on a decision of the author, `[-]` dropped (with a reason). Never delete a step. A step that needs a decision gets a question in the `decision/levelN.md` of its level.

**By case (D-196).** The ranks decide what to take; the way through one piece of work depends on its kind.

| Kind of work | Way through |
|---|---|
| A screen or an interface feature | **visual design first** (a drawing, reviewed by the author) → plan entry → code → tests of the logic → spec of the new messages → manual → tutorial |
| A language or compiler feature | feature in `spec/features/` → design (decision with examples) → failing test → compiler → spec → manual → tutorial |
| A library module | plan (`design-libraries.md`) → failing test → code → spec page → manual |
| A bug | failing test → fix |
| A refactor | tests green → move → tests green; no change of behavior; its own commit |
| An optimization | `bmark.py` before → change → `bmark.py` after |

## Ground rules

- **The spec is normative, the tutorial is didactic.** When they disagree, the spec wins and the tutorial is fixed, after the author approves the decision.
- **Source of truth for tables is JSON** (`spec/lexical/*.json`, `spec/features/*.json`, `test/<suite>/<suite>.json`). Tables in the manual and the tutorial are generated from it, not edited by hand.
- **Authors own the syntax and the decisions.** Do not replace the author's syntax with a proposal; raise a question in `decision/levelN.md`.
- **Evidence over memory.** Extract facts with scripts (`temp/`) and cite the source file in the result of a step.
- **Tutorial changes are committed in the scl repo** (`git -C tutorial …`); everything else in eve-lang.
